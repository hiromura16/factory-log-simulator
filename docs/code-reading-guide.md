# コードを読む順番とデータの流れ

## まず一本の流れを追う

`app.py` → `studio.create_app()` → `Store` と `Controller` → 種類別ドライバー、という順で読みます。ASGI（Webサーバーから要求を受け取る接続仕様）の入口は `app:app` です。起動しただけで外部送信するとは限らず、保存された希望状態と開始要求が実行を決めます。

```text
ブラウザー index.html + style.css + app.js
  ├─ 編集値 → preview → 検証済み設定・見本（開始とは別）
  ├─ profile/preset保存 → Store → SQLite・暗号化した接続設定
  └─ start/stop → Controller → generator → 種類別driver → 保存/公開/送信
                         └─ 状態・メトリクス → 画面の定期取得
外部の取得クライアント → data_api → 認証・条件解析・カーソル検証 → Store
```

## 入口から実装へ

| 読む場所 | 入出力と役割 | 読み違えやすい境界 |
|---|---|---|
| `models.py` / `config.py` | 接続・実行・生成規則の入力を検証 | Pydantic（型付き入力検証）のクラス文書は公開schemaに出るため、説明をコメントにしている |
| `studio.py` / `helptext.py` | 管理API・画面向けschema・入力説明 | 管理操作とデータ取得側の認証は同じ話ではない。秘密値を応答へ戻さない処理を追う |
| `generation.py` | 規則・シード・連番からレコードを組み立てる | 同じ識別条件の再現性、型変換エラー、異常注入を分けて読む |
| `controller.py` | 開始停止、資源ガード、実行状態を調停 | 保存した希望状態と現在の状態は別。停止待ちや失敗時の状態遷移も確認する |
| `drivers.py` / `equipment.py` | 種類に応じた記録・イベント・プロトコル処理 | 外部送信、再試行、相手側確認の範囲を区別する。単なる受信確認は業務処理の完了を保証しない |
| `store.py` | 設定・履歴・進捗を永続化 | SQLiteの更新単位、秘密の維持、カーソル署名は別の責務。署名は暗号化ではない |
| `data_api.py` | REST/OData/履歴の取得要求を処理 | フィルターをSQL文字列へ直結せず解析する。ページ間のスナップショットと差分取得を区別する |
| `connection_security.py` | 秘密値・接続ファイル・TLS設定を解決 | 接続に使う資格情報は画面表示用の値とは分けて扱う |
| `static/app.js` | schemaからフォームを作り、操作をAPIに渡す | フォーム編集だけでは保存・開始しない。監視失敗は周期処理で抑え、利用者操作の失敗は表示する |

## 開発・実行用ファイル

- `scripts/init_local.py`: `.env.example`からローカル環境ファイルを排他的に新規作成します。既存ファイルを上書きしません。`__doc__` はCLIヘルプに使われるため元の表示を保持しています。
- `scripts/export_contracts.py`: UI用schemaを `contracts/` へ書き出します。実行すると生成物が変わるため、解説追加の検証では生成を行いません。
- `build_presets.py`: `presets/` の見本設定を生成します。アプリを動かす入口ではありません。
- `Dockerfile`: 依存を含むイメージの構築と実行条件。`compose.yaml` はJSON構文で記述したCompose定義なので、JSONを壊すコメントは足していません。
- `pyproject.toml` / `requirements.txt` / `uv.lock`: 依存と再現性。lockfileは生成物なので編集対象外です。

## ログの整形と配送状態

`studio.py` の `/api/preview` は、`drivers.py` の `EventDriver.log_payload()` と `syslog_tcp_frame()` を使います。整形した本文のUTF-8バイト数と、TCP/TLSで送る際に区切りを含めたバイト数を確認できます。時刻には見本用の値を使い、配送キューへは書き込みません。

ファイル出力の書き込みやローテーションに失敗すると、イベントは `pending` のまま残ります。後続の再試行で出力が成功したときに `delivered` へ更新します。[ログの回帰テスト](../tests/test_log_preview.py)で、プレビューと配送失敗からの再試行を確認できます。

## テストで境界を確かめる

`tests/conftest.py` が保存先・環境をテストごとに隔離し、`test_studio.py` が秘密を応答へ出さないこと、プリセット・プレビュー、ページ取得と差分、履歴集計、異常応答を確かめます。種類別テストがあるリポジトリでは実プロトコルの通信、ラベルやイベントの連番なども追います。テストが通っても全接続先や負荷条件が保証されたことにはなりません。

## 注釈の対象と対象外

手書きPython（ネスト・async・テストを含む）とJavaScriptの全関数・コールバックを対象にしています。HTML/CSS・Docker・依存定義は役割を説明しています。モジュールや関数の説明は戻り値だけでなく、保存・送信・DOM更新などの副作用と失敗の扱いも併せて読みます。
